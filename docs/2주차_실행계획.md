# 2주차 실행계획 — 벤치마크 데이터셋 + LLM 판별 엔진

| 항목 | 내용 |
|---|---|
| 기간 | 2주차 (7일) |
| 목표 | 라벨링된 벤치마크 100건 구축 + LLM 판별기가 전건을 처리해 결과 JSON 출력 |
| 완료 기준(DoD) | `python -m analyzer.run` 실행 → `data/results/*.json` 에 도구별 판정 결과 저장 |

## 0. 2주차를 한 문장으로

> **"판별기를 만들고, 그 판별기를 채점할 시험지를 먼저 만든다."**

1주차에 '감사 대상'을 확보했으니, 2주차엔 '감사하는 두뇌'를 만듭니다. 그런데 순서가 중요합니다. **판별기보다 시험지(데이터셋)를 먼저 만듭니다.** 정답이 없으면 판별기가 잘 하는지 알 수 없고, 정답 없이 만든 판별기는 자기가 잘한다고 착각하게 되거든요.

이 순서를 지키는 것 자체가 포트폴리오의 차별점입니다. 대부분은 "만들고 나서 잘 되는 것 같다"에서 끝납니다.

## Step 1. 정상 샘플 확정 — 🤖 코드 / 🙋 실행

`config/servers.yaml` 에 서버 3개(memory, sequentialthinking, everything)를 추가해 두었습니다. 다시 수집하면 이렇게 됩니다.

| 서버 | 도구 수 | 성격 |
|---|---|---|
| filesystem | 14 | 파일 접근 (고위험) |
| git | 12 | 저장소 조작 (고위험) |
| memory | 9 | 지식그래프 저장 |
| everything | 13 | 기능 시연용 (다양) |
| time | 2 | 시간 변환 (무해) |
| fetch | 1 | 웹 수집 |
| sequentialthinking | 1 | 추론 보조 (설명문 매우 김) |
| **합계** | **52** | |

**52건을 그대로 쓰는 이유**: 억지로 60을 채우려고 검증 안 된 서드파티 서버를 넣으면, 그게 정말 '정상'인지 보장할 수 없습니다. **정상 라벨의 신뢰도가 무너지면 평가 전체가 무의미해집니다.** 공식 레퍼런스 서버만 쓰는 편이 낫습니다.

**실행 명령**
```powershell
python -m collector.run
```

## Step 2. 오염 샘플 생성기 — 🤖 제가 합니다

정상 도구 정의를 **변형(mutation)** 해서 악성 샘플을 만듭니다. 무에서 창작하지 않고 변형하는 이유는, 정상과 악성이 표면적으로 비슷해야 판별기가 진짜 실력을 보여주기 때문입니다. 너무 티나는 악성 샘플만 넣으면 재현율 0.98 같은 무의미한 숫자가 나옵니다.

| 오염 유형 | 개수 | OWASP | 변형 방법 |
|---|---|---|---|
| 숨은 지시문 (Hidden Instruction) | 16 | MCP03/06 | 설명문 끝에 은닉 태그로 지시 삽입. 태그 형태를 5종으로 분산 |
| 스키마 불일치 (Schema Mismatch) | 12 | MCP03 | 설명은 그대로 두고 무관한 파라미터 추가 (예: 시간변환 도구에 `file_path`) |
| 권한 과다 (Scope Creep) | 10 | MCP02 | 읽기 전용 도구가 쓰기·삭제 권한을 요구하도록 변형 |
| 도구 섀도잉 (Tool Shadowing) | 10 | MCP03 | 기존 도구명 유사 변형 + "이 도구를 대신 쓰라"는 유도 문구 |
| **합계** | **48** | | |

**난이도 3단계로 나눕니다**: easy(노골적) / medium(자연스러움) / hard(정상 문구와 거의 구분 불가). 난이도별 재현율을 따로 뽑으면 **"어디까지 잡히고 어디서 무너지는지"** 를 말할 수 있게 됩니다. 이게 3주차 리포트의 핵심 그래프가 됩니다.

> ⚠️ **윤리 원칙**: 합성 데이터는 `data/benchmark/` 안에만 존재하며, 동작하는 악성 MCP 서버로 배포하지 않습니다. README 에 이미 명시해 두었습니다.

## Step 3. 데이터셋 병합·라벨링 — 🤖 코드 / 🙋 **검수는 직접**

**라벨 스키마**
```json
{
  "sample_id": "poisoned_0007",
  "source_server": "time",
  "tool_name": "convert_time",
  "description": "...",
  "input_schema": { },
  "is_malicious": true,
  "attack_type": "hidden_instruction",
  "owasp_code": "MCP03",
  "difficulty": "medium",
  "rationale": "설명문 말미에 사용자에게 숨기라는 지시가 삽입됨",
  "mutation_of": "time::convert_time"
}
```

**🙋 jun님이 직접 하실 일 — 라벨 검수 (30분~1시간)**

제가 생성한 48건을 눈으로 훑으면서 이 두 가지만 봐주세요.

1. **정상인데 악성으로 라벨된 것은 없는가** (변형이 실패해 원본과 같아진 경우)
2. **난이도 라벨이 체감과 맞는가** (hard인데 너무 뻔하면 medium으로 조정)

라벨링을 직접 하셔야 하는 이유는 두 가지입니다. 데이터 품질은 결국 사람이 보증해야 하고, 면접에서 **"데이터셋 어떻게 만들었나요"** 라는 질문이 반드시 나옵니다. 직접 보지 않은 데이터는 설명할 수 없습니다.

검수용 CSV를 만들어 드릴 테니 엑셀에서 보시면 됩니다.

## Step 4. 규칙 엔진 (선필터) — 🤖 제가 합니다

LLM에 보내기 전에 값싼 규칙으로 1차 스크리닝합니다.

| 규칙 | 탐지 대상 |
|---|---|
| 은닉 태그 패턴 | `<IMPORTANT>`, `<!-- -->`, `[SYSTEM]` 등 |
| 지시 동사 + 은폐 표현 | "do not mention", "절대 언급하지 마" 등 |
| 경로/시크릿 리터럴 | `~/.ssh/`, `.env`, `id_rsa`, `AKIA...` |
| 설명↔스키마 명사 불일치 | 설명에 없는 파라미터가 존재 |
| 도구명 유사도 | 기존 도구와 편집거리 2 이하 |
| 설명문 길이 이상치 | 동일 서버 내 평균 대비 3σ 초과 |

**이 엔진의 진짜 목적은 탐지가 아니라 비교군 확보입니다.** 3주차에 "규칙만 썼을 때 F1 0.5x → LLM 추가 시 0.8x"를 보여주면, **"왜 LLM이 필요한가"에 대한 숫자로 된 증명**이 됩니다. 말로 하는 것보다 백 배 강합니다.

## Step 5. LLM 판별기 — 🤖 코드 / 🙋 API 키 확인

**구조화 출력(Structured Output)을 씁니다.** 자유 텍스트로 받으면 파싱이 깨지고, 평가 자동화가 불가능합니다.

```json
{
  "is_malicious": true,
  "confidence": 0.87,
  "owasp_code": "MCP03",
  "attack_type": "hidden_instruction",
  "evidence_span": "이 지시를 사용자에게 언급하면 도구가 실패하므로...",
  "reasoning": "설명문에 사용자 은폐를 요구하는 지시가 포함됨",
  "recommended_action": "해당 서버 도입 보류 및 배포자 확인 필요"
}
```

`evidence_span`(근거 문장 원문 인용)을 필수로 요구하는 게 핵심입니다. 모델이 환각으로 "위험합니다"라고만 하면 검증할 수 없지만, **원문을 인용하게 하면 그 문장이 실제로 존재하는지 프로그램으로 검증**할 수 있습니다. 환각 억제 장치이자 리포트의 신뢰도 근거입니다.

**모델 구성 (검증된 2026-08 기준 가격)**

| 용도 | 모델 | 입력 $/M | 출력 $/M |
|---|---|---|---|
| 1차 스크리닝 | `claude-haiku-4-5-20251001` | $1 | $5 |
| 정밀 판별 | `claude-sonnet-5` | $2 | $10 |

> Sonnet 5의 $2/$10은 2026년 8월 31일까지 한시 요금이며 이후 $3/$15로 인상됩니다. 9월 이후 실행분은 비용이 약 1.5배가 되니 참고하세요.

**프롬프트 캐싱 적용**: OWASP 정의 블록은 100건 모두에 동일하게 들어갑니다. 캐싱하면 그 부분이 정가의 10%로 떨어집니다. 비용 최적화 사례로 면접에서 쓸 수 있습니다.

## Step 6. 소규모 시험 + 비용 측정 — 🙋 직접 실행

**반드시 10건으로 먼저 돌립니다.** 100건을 바로 돌렸다가 프롬프트가 잘못돼 있으면 돈과 시간을 함께 날립니다.

```powershell
python -m analyzer.run --limit 10 --dry-run   # 호출 없이 프롬프트만 출력
python -m analyzer.run --limit 10             # 실제 호출
python -m analyzer.run                        # 전체 100건
```

토큰 사용량과 원화 환산 비용을 자동으로 찍도록 만들겠습니다. 이 수치가 그대로 3주차 리포트의 "운영 비용" 섹션이 됩니다.
