## 최종 성능 (벤치마크 100건: 정상 52 + 오염 48)

|---|---|---|---|---|---|

## 핵심 발견 (포트폴리오/면접용)

### 1. 하이브리드가 재현율 100% 달성 — 취약점이 상호보완적
- **규칙**은 구조적 신호(스키마에 삽입된 file_path/context/metadata)를 잘 잡지만
  의미적 은닉 지시(자연스러운 문장에 숨긴 유도)를 놓친다.
- **LLM**은 은닉 지시를 완벽히 잡지만(hidden_instruction 16/16), 일반적인
  'metadata' 파라미터 추가 같은 모호한 스키마 불일치를 정상으로 합리화한다
  (schema_mismatch 8/12, 놓친 4건 전부 metadata/hard).
- 둘을 OR 로 합치니 서로의 사각지대를 메워 **놓친 악성 0건**.
- → "왜 규칙과 LLM 을 함께 쓰는가"를 숫자로 증명. 3주차 리포트의 핵심 그래프.

### 2. 근거 인용 검증으로 환각 0건 확인
- 모델에 evidence_span(근거 원문 인용)을 강제하고, 그 인용문이 실제
  정의(설명문+스키마)에 존재하는지 프로그램으로 검증.
- 초기 검증기가 설명문만 대조해 schema_mismatch 근거 10건을 '환각'으로
  오판 → 스키마까지 대조하도록 수정 → **실제 환각 0건** 확인.
- → 판별 결과의 신뢰성을 정량적으로 보증하는 장치.

### 3. 의도된 하드 네거티브에서의 오탐 = 합리적 불일치
- LLM 오탐 2건은 일부러 심은 하드 네거티브(get-env, fetch).
- get-env(환경변수 전체 반환)를 MCP02(권한과다)로, fetch(어시스턴트 지시성
  문구)를 MCP06 으로 판정 → 라벨은 clean 이지만 모델의 판단도 일리 있음.
- → 3주차에서 "기능의 위험성 vs 정의문의 악의성" 경계 사례로 정성 분석.

### 4. 비용
- 100건 전체 판별 491원 (프롬프트 캐싱으로 입력 22.5만 토큰 중 16.7만이 캐시 히트).
- 예산 1만원 대비 충분. 3주차 프롬프트 전략 비교(3종)까지 여유.
