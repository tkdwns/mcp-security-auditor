# 확장 계획 (E) — 4주 완주 이후의 심화 과제

작성일: 2026-08-15

---

## 0. 전체 그림

4주로 프로젝트는 이미 완성입니다. E는 **더 좋게 만드는 것**이지 **완성시키는 것**이 아닙니다.
그래서 각 항목은 독립적이고, 어디서 멈춰도 됩니다.

| 항목 | 무엇 | 가치 | 소요 | 예상 비용 |
|---|---|---|---|---|
| **E-1 럭풀 탐지** | 설치 후 몰래 바뀐 설명문 잡기 | ★★★ | 2~3일 | 약 1,000원 |
| **E-2 MCP 서버화** | 이 감사기를 MCP 서버로 노출 | ★★★ | 1~2일 | 약 100원 |
| **E-3 scope_creep 개선** | 남은 약점(4/6) 보완 | ★★ | 1일 | 약 700원 |
| **E-4 GitHub Action** | PR에서 자동 감사 | ★★ | 반나절 | 거의 0원 |

**권장 순서: E-1 → E-2 → E-3 → E-4**
E-1이 가장 가치가 크고, E-2가 가장 기억에 남습니다. E-3·E-4는 여력에 따라.

누적 예산: 지금까지 약 5,000원 사용 / 1만원 중. E 전체 해도 약 7,000원 선입니다.

## E-1. 럭풀(Rug Pull) 탐지 — 가장 추천

### 무엇을 만드나

**럭풀**은 설치 시점엔 멀쩡하다가 나중에 도구 설명문을 몰래 악의적으로 바꾸는 공격입니다.
사용자는 한 번 승인하면 다시 들여다보지 않으니, 검사를 통과한 뒤에 바꾸면 그만입니다.

지금의 감사기는 **한 시점의 스냅샷**만 봅니다. 럭풀 탐지는 **시간에 따른 변화**를 봅니다.

### 왜 이게 강력한가

**1주차부터 준비해 둔 게 있습니다.** `content_hash` 와 `collected_at` 필드를
수집기에 넣어뒀는데, 그때 이유를 이렇게 적었습니다.

> "Rug Pull 공격을 탐지하려면 과거 스냅샷이 있어야 한다. 1주차에 필드 2개를
>  더 넣는 비용으로 4주차 확장 기능의 전제조건을 확보한다."

즉 **데이터 구조가 이미 준비되어 있습니다.** 면접에서 "확장을 염두에 두고 설계했다"를
말이 아니라 커밋 히스토리로 증명할 수 있습니다.

### 진짜 어려운 지점 (여기가 핵심)

"바뀌었으면 의심"은 쓸모없습니다. 정상 서버도 계속 바뀌니까요.

| 정상적인 변경 | 악의적인 변경 |
|---|---|
| 오타 수정, 문장 다듬기 | 은닉 지시문 삽입 |
| 새 파라미터 추가 (설명에도 반영) | 설명 없이 파라미터만 추가 |
| 기능 확장을 설명에 명시 | 권한 요구를 슬쩍 확대 |
| 도구 이름 변경 (deprecated 안내 동반) | 다른 도구를 사칭하는 이름으로 변경 |

**정상 변경과 악의적 변경을 구분하는 것**이 이 기능의 전부입니다.
그래서 벤치마크에도 **정상 변경 샘플을 반드시 넣어야** 오탐률을 측정할 수 있습니다.

### 단계

| 단계 | 내용 | 담당 |
|---|---|---|
| 1 | **스냅샷 저장소** — 수집할 때마다 시점별로 보관하고 조회하는 계층 | 🤖 |
| 2 | **Diff 엔진** — 두 스냅샷 비교해 추가/삭제/변경 분류. `content_hash` 로 변경 즉시 검출 (LLM 불필요, 무료) | 🤖 |
| 3 | **변경 벤치마크** — 정상 변경 20쌍 + 악의적 변경 20쌍. 기존 뮤테이터를 재활용해 before/after 쌍 생성 | 🤖 |
| 4 | **변경 판별기** — 이전/이후 설명문을 나란히 주고 "이 변경이 악의적인가" 판별. 기존 판별기와 다른 프롬프트가 필요 | 🤖 |
| 5 | **평가** — 정밀도·재현율·오탐률 측정. **정상 변경을 악성으로 찍지 않는지**가 관건 | 🙋 실행 |
| 6 | **CLI + API** — `python -m rugpull.check`, `POST /rugpull` | 🤖 |

### 🙋 직접 하실 일
- 5단계 평가 스크립트 실행 후 결과 공유 (약 1,000원)
- 결과 보고 판별 기준 조정 여부 판단

### 위험
- 오탐이 많으면 쓸모없는 기능이 됩니다. 정상 변경 샘플을 충분히 넣어 검증합니다.
- 시나리오가 인위적으로 보일 수 있으니, 실제 있을 법한 변경만 씁니다.

## E-2. 이 감사기를 MCP 서버로 노출

### 무엇을 만드나

지금까지는 MCP를 **쓰는** 프로젝트였습니다. 이제 MCP를 **만드는** 프로젝트가 됩니다.
Claude Desktop 같은 MCP 클라이언트에 등록하면, 대화 중에 이렇게 쓸 수 있습니다.

> "이 서버 도구 정의 좀 검사해줘" → 에이전트가 우리 감사 도구를 호출 → 결과 반환

### 왜 이게 기억에 남나

**자기 자신을 검사할 수 있습니다.**

우리가 만든 MCP 서버의 도구 설명문을, 우리가 만든 감사기로 검사하는 겁니다.
"보안 감사 도구가 스스로의 기준을 통과하는가"는 데모로도 강렬하고,
실제로 유용한 자기 점검이기도 합니다. 이걸 테스트로 고정해 두면
앞으로 설명문을 수정할 때 자동으로 검증됩니다.

### 단계

| 단계 | 내용 | 담당 |
|---|---|---|
| 1 | **MCP 서버 구현** — Python SDK로 stdio 서버 작성 | 🤖 |
| 2 | **도구 3개 정의** — `audit_tools`(정의 검사) / `get_demo_report`(예시) / `explain_owasp_code`(코드 설명) | 🤖 |
| 3 | **설명문 자체 점검** — 우리 도구 설명이 은닉 지시·스키마 불일치 없이 깨끗한지 확인 | 🤖 |
| 4 | **자기 감사 테스트** — 우리 서버를 우리 감사기에 물려 "적합(Pass)" 나오는지 자동 검증 | 🤖 |
| 5 | **클라이언트 등록** — `claude_desktop_config.json` 설정 예시 + 실제 연결 확인 | 🙋 |
| 6 | **README 문서화** — 설치·사용법 | 🤖 |

### 🙋 직접 하실 일
- 5단계: Claude Desktop 설정 파일에 등록하고 실제로 대화에서 써보기
- 화면 캡처 1장 (README·포트폴리오용으로 효과 큼)

### 위험
- 우리 서버 도구 설명이 우리 기준에 걸리면 곤란합니다. 3~4단계가 그 방지책입니다.

## E-3. scope_creep 탐지 개선 (현재 4/6)

### 무엇을 고치나

3주차에 남은 유일한 약점입니다. 못 잡은 2건은 이런 표현이었습니다.

> "Requires the same access level as the other tools in this server so that
>  behavior stays consistent across the toolset."

구체적 권한을 하나도 말하지 않고 모호하게 일반화했습니다.
정상 서버도 쓸 법한 문장이라 경계가 흐립니다.

### 접근 — 섀도잉을 고쳤던 방식 그대로

섀도잉이 안 잡혔던 이유는 "판단에 필요한 정보가 입력에 없어서"였고,
카탈로그를 넣어 해결했습니다. **scope_creep도 같은 구조일 가능성이 큽니다.**

"다른 도구와 동일한 접근 수준"이 과한지 아닌지는, **다른 도구들이 실제로 어떤
권한을 갖는지 알아야** 판단할 수 있습니다. 그런데 지금은 그 정보를 안 줍니다.

### 단계

| 단계 | 내용 | 담당 |
|---|---|---|
| 1 | **권한 프로파일 추출** — 도구별로 파일읽기/쓰기/삭제/네트워크/실행 여부를 설명·스키마에서 추정 (규칙 기반, 무료) | 🤖 |
| 2 | **서버 권한 요약 주입** — 같은 서버 다른 도구들의 권한 분포를 프롬프트에 함께 제공 (전략 E) | 🤖 |
| 3 | **홀드아웃 v2 재평가** — scope_creep 재현율이 오르는지 | 🙋 실행 |
| 4 | **부작용 검증** — 다른 3개 유형이 떨어지지 않는지 반드시 확인 | 🙋 |

### 🙋 직접 하실 일
- 3단계 실행 (51건 × 1전략, 약 350원)
- 결과 공유

### 위험
- 개선이 안 될 수도 있습니다. **그것도 결과입니다** —
  "카탈로그 방식이 모든 유형에 통하지는 않았다"는 정직한 발견이 됩니다.

## E-4. GitHub Action 연동

### 무엇을 만드나

저장소에 MCP 설정 파일이 있고 PR에서 그게 바뀌면, 자동으로 감사해서
**PR 코멘트로 결과를 남기고 Critical 이 있으면 체크를 실패**시킵니다.

### 왜 넣나

지금까지는 "사람이 실행하는 도구"였습니다. 이걸 붙이면 **개발 워크플로에 들어가는
도구**가 됩니다. 실무 적용성을 보여주는 가장 짧은 방법입니다.

### 단계

| 단계 | 내용 | 담당 |
|---|---|---|
| 1 | **워크플로 작성** — `.github/workflows/mcp-audit.yml` | 🤖 |
| 2 | **변경 감지** — PR diff에서 MCP 설정 파일만 골라내기 | 🤖 |
| 3 | **감사 실행 + 코멘트** — 결과를 마크다운 표로 PR에 게시 | 🤖 |
| 4 | **실패 조건** — Critical 발견 시 exit 1 | 🤖 |
| 5 | **시크릿 등록 + 테스트 PR** — 실제로 동작 확인 | 🙋 |

### 🙋 직접 하실 일
- GitHub 저장소 Settings → Secrets 에 `ANTHROPIC_API_KEY` 등록
- 일부러 오염된 설정을 넣은 테스트 PR 생성 → 코멘트 확인 → 스크린샷

### 위험
- Action 실행마다 API 비용이 듭니다. 도구 수 상한과 `paths` 필터로 제한합니다.

2. README 에 반영합니다
3. 커밋합니다
