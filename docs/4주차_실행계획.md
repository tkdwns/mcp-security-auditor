## 0. 4주차를 한 문장으로

> **"내 컴퓨터에서만 되는 것"을 "누구나 링크로 써보는 것"으로 바꾼다.**

지금까지 만든 건 전부 CLI입니다. 채용 담당자가 이걸 보려면 저장소를 클론하고,
파이썬을 설치하고, API 키를 발급받아야 합니다. **아무도 안 합니다.**
링크 하나로 30초 안에 동작을 보여주는 것이 4주차의 전부입니다.

배포된 프로젝트가 강한 신호인 이유는 화려해서가 아니라, **배포는 대충 넘어갈 수
없는 것들을 강제하기 때문**입니다 — 비밀 관리, 타임아웃, 동시성, 비용 방어.
이것들을 처리한 흔적이 곧 실무 역량의 증거입니다.

## Step 0. 설계 결정 3가지 — 🤖 제안 / 🙋 승인

코드를 짜기 전에 정해야 할 것들입니다. 잘못 정하면 Step 5에서 되돌아와야 합니다.

### 결정 ① API가 MCP 서버에 직접 붙을 것인가?

| 방식 | 장점 | 단점 |
|---|---|---|
| **A. 도구 정의(JSON)를 입력받는다** ✅ 추천 | 이미지가 가볍다(파이썬만), 배포 간단, 어떤 서버든 검사 가능 | 사용자가 정의를 붙여넣어야 함 |
| B. 서버에 직접 접속해 수집한다 | 사용자가 서버 주소만 주면 됨 | 컨테이너에 Node.js + uv 필요, 임의 프로세스 실행 = 보안 위험 |

**추천: A.** 컨테이너 안에서 임의의 MCP 서버를 실행하는 건 그 자체로 위험합니다
(우리가 잡으려는 게 바로 악성 서버입니다). 라이브 수집은 로컬 CLI에 남겨두고,
API는 정의를 받아 판별만 합니다. **"보안 도구가 스스로 공격면을 줄인다"**는
설계 판단이라 README에 쓸 가치가 있습니다.

### 결정 ② 요청을 동기로 처리할까, 비동기로 할까?

도구 14개 감사에 **약 50초**가 걸립니다. 대부분의 PaaS는 30~60초에서 요청을
끊습니다. 동기로 두면 배포 직후 타임아웃으로 실패합니다.

**추천: 비동기.** `POST /audit` 는 즉시 `job_id`를 돌려주고, 클라이언트가
`GET /audit/{job_id}` 로 진행 상황을 폴링합니다. Step 2에서 구현합니다.

### 결정 ③ 어디에 배포할까? → **Render (확정)**

**결정 사항 (2026-08-15 확정)**
- 결정 ① : **A. 도구 정의(JSON) 입력 방식** — API는 MCP 서버에 접속하지 않는다
- 결정 ② : **비동기** — job_id 반환 + 폴링
- 결정 ③ : **Render 무료 플랜**, 단 *완전 무료* 유지가 조건

#### Render 무료 플랜 실제 제약 (공식 문서 확인, 2026-08 기준)

| 항목 | 값 | 우리 프로젝트 영향 |
|---|---|---|
| 인스턴스 시간 | **750시간/월 (워크스페이스 전체)** | 상시 가동 1개 = 744시간 → **서비스는 1개만** |
| 유휴 슬립 | 15분 무트래픽 시 슬립, 복귀 약 1분 | README에 "첫 요청 1분" 안내 필요 |
| 아웃바운드 대역폭 | **5GB/월** (2026년 4월 100GB → 5GB로 축소) | JSON 텍스트 위주라 여유. **이미지는 앱에서 서빙 금지** |
| 리소스 | RAM 512MB / 0.1 vCPU | 무거운 라이브러리 배제 필요 (아래 참조) |
| 초과 시 | GB당 $0.15 청구, **결제수단 없으면 서비스 중단** | ← 이것이 완전 무료의 보장 장치 |

#### "완전 무료" 유지 체크리스트

- [ ] **결제수단을 등록하지 않는다.** 초과가 나도 청구되지 않고 서비스만 멈춘다.
      (단, 가입 단계에서 카드 확인($1 승인)을 요구할 수 있다. 요구되면 알려줄 것)
- [ ] **웹 서비스 1개만** 만든다. 두 개면 750시간을 나눠 써 월말에 둘 다 멈춘다.
- [ ] **DB를 붙이지 않는다.** 무료 Postgres 는 30일 후 자동 만료라 어차피 못 쓴다.
      작업 상태는 인메모리로 충분하다(Step 2 설계와 일치).
- [ ] **차트 이미지는 GitHub README 에서만 서빙**한다. 앱에서 내보내면 대역폭을 먹는다.
- [ ] Docker 이미지를 작게 유지한다(빌드 파이프라인 시간도 무료 한도를 소비).

#### 512MB 제약이 만드는 설계 결정

API 컨테이너에는 **pandas · scikit-learn · matplotlib 을 넣지 않습니다.**
이들은 실험·시각화 전용이며 판별에는 필요 없습니다.
→ `requirements-api.txt` 를 따로 만들어 `fastapi · uvicorn · anthropic · pydantic`
   정도만 담습니다. 이미지가 가벼워지고 메모리도 여유가 생깁니다.
→ "런타임에 필요한 것과 개발에 필요한 것을 분리했다"는 판단이라 README 에 적을 가치가 있습니다.

## Step 1. FastAPI 골격 + 엔드포인트 — 🤖 코드 / 🙋 로컬 실행

| 엔드포인트 | 역할 |
|---|---|
| `GET /health` | 헬스체크 (배포 플랫폼이 요구) |
| `POST /audit` | 도구 정의 목록을 받아 감사 시작 → `job_id` 반환 |
| `GET /audit/{job_id}` | 진행률·결과 조회 |
| `GET /audit/{job_id}/report.md` | 마크다운 리포트 다운로드 |
| `GET /demo/{kind}` | 미리 만들어 둔 샘플 결과 (**API 호출 없음, 무료**) |
| `GET /` | 웹 UI |

**`/demo` 를 따로 두는 이유**: 채용 담당자가 링크를 눌렀을 때 **API 키 없이도,
비용 없이도** 결과를 볼 수 있어야 합니다. 3주차에 만든 리포트 3종을 정적으로
서빙합니다. 이게 실제로 가장 많이 눌릴 버튼입니다.

**🙋 하실 일**: `uvicorn api.main:app --reload` 실행 후 `http://localhost:8000/docs`
접속. FastAPI가 자동 생성한 API 문서가 뜨면 성공입니다.

## Step 2. 비동기 작업 처리 — 🤖 코드 / 🙋 실행

**동작 방식**

```
POST /audit  ──▶ job 생성(메모리) ──▶ 즉시 {job_id, status:"queued"} 반환
                      │
                      └─▶ BackgroundTasks 로 감사 실행
                                │
GET /audit/{id} ──▶ {status:"running", progress:"7/14"} ──▶ ... ──▶ {status:"done", result:{...}}
```

FastAPI의 `BackgroundTasks`를 씁니다. Celery나 Redis는 이 규모에 과합니다.
**과한 기술을 안 쓴 것도 판단이므로 README에 이유를 적습니다.**

한계도 명시합니다: 인메모리 저장이라 **재시작하면 작업이 사라집니다.**
프로덕션이라면 Redis나 DB가 필요하다는 걸 안다는 표시입니다.

## Step 3. 비용·남용 방어 — 🤖 코드 ★ 이 단계를 건너뛰면 안 됩니다

**공개 URL에 내 API 키가 물려 있습니다.** 누군가 스크립트로 반복 호출하면
비용이 그대로 청구됩니다. 실제로 자주 일어나는 사고입니다.

| 방어 | 내용 |
|---|---|
| 요청당 도구 수 상한 | 최대 20개 (초과 시 400) |
| IP당 요청 제한 | 시간당 3회 |
| 일일 총 호출 상한 | 예: 200콜 도달 시 데모 모드로 자동 전환 |
| 입력 크기 제한 | 요청 본문 최대 256KB |
| 예산 소진 시 동작 | 에러 대신 **캐시된 데모 결과**를 반환하고 안내 문구 표시 |

마지막 항목이 중요합니다. 예산이 떨어졌을 때 500 에러가 나면 "고장난 프로젝트"로
보이지만, 데모 결과로 우아하게 폴백하면 **의도된 설계**로 보입니다.

## Step 4. 웹 UI — 🤖 코드 / 🙋 확인

단일 HTML 페이지 하나. 프레임워크 없이 순수 HTML+JS로 만듭니다.

- 왼쪽: 도구 정의 JSON 붙여넣기 (샘플 채우기 버튼 3개 — 정상/악성/혼합)
- 오른쪽: 감사 결과 (위험 등급 배지, 근거 인용, 권고 조치)
- 상단: "데모 보기" 버튼 (API 키 불필요)

**React를 안 쓰는 이유**: 빌드 단계가 생기면 Docker 이미지가 복잡해지고
배포 실패 지점이 늘어납니다. 화면 하나에 그 비용을 낼 이유가 없습니다.

## Step 5. Docker + 배포 — 🤖 코드 / 🙋 계정 연결

**Dockerfile 설계 포인트**

- `python:3.11-slim` 베이스 (Node.js 불필요 — 결정 ①의 이득)
- 의존성 레이어를 코드보다 먼저 복사해 **빌드 캐시 활용**
- **API 키를 이미지에 넣지 않습니다.** 런타임 환경변수로 주입합니다.
  (`.dockerignore` 에 `.env` 포함 — 이걸 빠뜨리면 키가 이미지에 박힙니다)
- 비루트 사용자로 실행

**🙋 하실 일**
1. Render 가입 → GitHub 저장소 연결
2. 환경변수 `ANTHROPIC_API_KEY` 등록 (**대시보드에서만, 코드에 절대 금지**)
3. 배포 후 URL 확인 → 공유

**리스크**: 첫 배포는 거의 항상 한 번은 실패합니다(포트, 헬스체크, 의존성).
로그를 그대로 주시면 바로 잡아드립니다.

여력이 되면 이어서 할 만한 것들입니다. 안 해도 포트폴리오는 완성됩니다.

3. **scope_creep 개선** — 3주차에 남은 유일한 약점(4/6). 같은 서버 다른 도구의
   권한 수준을 함께 제시하는 방향.
4. **GitHub Action** — PR 올릴 때 MCP 설정 변경을 자동 감사.
