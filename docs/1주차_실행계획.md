# 1주차 실행계획 — MCP 수집기(Collector) 구축

| 항목 | 내용 |
|---|---|
| 기간 | 1주차 (7일) |
| 목표 | 공식 MCP 서버 3개에 연결해 도구 정의를 JSON으로 덤프 성공 |
| 완료 기준(DoD) | `python -m collector.run` 실행 → `data/raw/*.json` 에 도구 목록 저장됨 |
| 예상 API 비용 | **거의 0원** (1주차는 LLM 호출 없음, 순수 연결·수집 단계) |

---

## 0. 1주차를 한 문장으로

> **"감사할 대상을 먼저 확보한다."**

우리가 만들 것은 MCP 서버의 도구 설명문을 검사하는 에이전트입니다. 검사하려면 먼저 **도구 설명문을 긁어올 수 있어야** 합니다. 1주차는 그 수집기를 만드는 주간입니다. LLM은 아직 등장하지 않습니다 — 2주차부터입니다.

이 순서가 중요한 이유는, 수집기가 없으면 2주차 데이터셋도 3주차 평가도 전부 공중에 뜨기 때문입니다. 1주차 산출물인 JSON 덤프가 그대로 2주차 데이터셋의 "정상 샘플 60건"이 됩니다.

## Step 1. 프로젝트 골격 생성 — 🤖 제가 합니다

`C:\Users\User\Desktop\MCP Proj` 안에 아래 구조를 만듭니다.

```
MCP Proj/
├─ .env                  # API 키 (절대 커밋 금지)
├─ .env.example          # 키 없이 형식만 (커밋 대상)
├─ .gitignore
├─ requirements.txt
├─ README.md
├─ config/
│   └─ servers.yaml      # 검사 대상 MCP 서버 목록
├─ collector/
│   ├─ __init__.py
│   ├─ models.py         # 도구 정의 스키마 (Pydantic)
│   ├─ client.py         # MCP 클라이언트 래퍼
│   └─ run.py            # 실행 진입점
├─ data/
│   └─ raw/              # 수집된 JSON 덤프 저장
└─ docs/
    └─ 과제정의서_v2.md
```

**⚠️ 보안 주의**: 이 프로젝트는 "시크릿 노출"을 잡아내는 보안 프로젝트입니다. 정작 본인 리포에 API 키를 커밋하면 면접에서 치명적입니다. `.gitignore`에 `.env`를 넣는 것을 Step 1에서 가장 먼저 처리합니다.

## Step 2. MCP 서버 1개 연결 — 🤖 코드 / 🙋 실행

가장 간단한 **Filesystem 서버**부터 붙입니다.

**동작 원리 (개념)**

```
[내 Python 스크립트]  ──stdio(표준입출력)──▶  [npx로 띄운 Filesystem 서버]
        │                                              │
        │  ① initialize() : 핸드셰이크                  │
        │  ② list_tools() : "너 무슨 도구 있어?"        │
        │◀── 도구 이름·설명·스키마 목록 반환 ───────────│
```

여기서 핵심은 **stdio 전송 방식**입니다. 서버를 네트워크로 띄우는 게 아니라, 내 프로그램이 자식 프로세스로 서버를 실행하고 표준입출력으로 대화합니다. 로컬 MCP 서버의 기본 방식이에요.

**jun님이 하실 일**: 제가 준 스크립트를 실행하고 → 터미널 출력을 저에게 붙여넣기. 에러가 나면 그 에러 메시지를 그대로 주시면 됩니다. (Windows에서 `npx` 경로 문제가 자주 나는데, 흔한 이슈라 대응법을 준비해두겠습니다.)

**이 단계 완료 신호**: 터미널에 `read_file`, `write_file`, `list_directory` 같은 도구 이름들이 주르륵 출력됩니다.

## Step 3. 수집기 구현 — 🤖 코드 / 🙋 실행

Step 2가 "출력해보기"였다면, Step 3은 **구조화해서 저장하기**입니다.

수집할 필드는 이렇습니다.

| 필드 | 설명 | 왜 필요한가 |
|---|---|---|
| `server_name` | 서버 식별자 | 어느 서버 소속인지 |
| `tool_name` | 도구 이름 | 도구 섀도잉 탐지에 사용 (이름 유사도) |
| `description` | **도구 설명문** | ★ 숨은 지시문 탐지의 핵심 대상 |
| `input_schema` | 파라미터 JSON Schema | 설명↔스키마 불일치 판별 대상 |
| `raw` | 원본 전체 | 나중에 필드 추가해도 재수집 불필요 |
| `collected_at` | 수집 시각 | **럭풀 탐지용** — 나중에 재수집해 diff 비교 |
| `content_hash` | 정의 해시값 | 변경 감지 (해시만 바뀌면 정의가 바뀐 것) |

**`content_hash`와 `collected_at`이 왜 지금 필요한가**: 확장 기능인 "럭풀 탐지"(설치 후 설명문이 몰래 바뀌는 공격)를 나중에 붙이려면 **지금부터 스냅샷을 쌓아야** 합니다. 1주차에 필드 2개 더 넣는 비용으로 4주차 차별화 기능을 살릴 수 있습니다.

**출력 예시** (`data/raw/filesystem_20260814.json`)

```json
{
  "server_name": "filesystem",
  "collected_at": "2026-08-14T15:30:00+09:00",
  "tools": [
    {
      "tool_name": "read_file",
      "description": "Read the complete contents of a file...",
      "input_schema": { "type": "object", "properties": { "path": {"type": "string"} } },
      "content_hash": "a3f2b8..."
    }
  ]
}
```

## Step 4. 서버 3개로 확장 — 🤖 코드 / 🙋 실행

`config/servers.yaml` 하나만 고치면 대상이 추가되도록 설계합니다.

```yaml
servers:
  - name: filesystem
    command: npx
    args: ["-y", "@modelcontextprotocol/server-filesystem", "C:\\Users\\User\\Desktop\\MCP Proj\\sandbox"]
  - name: fetch
    command: uvx
    args: ["mcp-server-fetch"]
  - name: git
    command: uvx
    args: ["mcp-server-git", "--repository", "."]
```

**서버 3개를 고른 기준**: 공식 레퍼런스 서버 중 현재도 유지보수되는 것들입니다. GitHub·Slack·Google Drive 서버는 archived 상태라 제외했습니다. 세 서버는 성격이 달라서(파일 접근 / 네트워크 접근 / 코드 저장소 접근) 위험 유형이 다양하게 나옵니다 — 데이터셋 다양성 확보에 유리합니다.

**⚠️ 안전 조치**: Filesystem 서버에는 **`sandbox` 폴더만** 접근 권한을 줍니다. 실수로 바탕화면 전체를 열어주면 안 됩니다. 이것도 리포트에 "안전한 검사 환경 설계"로 쓸 수 있는 대목입니다.
